Each example below describes work I authored personally. Where a codebase was shared with a team, the scope stated is my own contribution, not the team’s.

Education platform · Architecture Tested state machine for a multi-phase session flow
Problem
A guided multi-phase learning session had rules about which step could follow which. Left in the components, that logic spreads across the render tree as conditionals and becomes impossible to test or reason about.
Contribution
Designed the flow as a headless, framework-independent state machine with a typed phase union and explicit transition guards, then wrote its unit test suite. Illegal transitions throw rather than putting the session into an undefined state.
Outcome
The session rules live in one tested module instead of the component tree, so the interface renders state rather than arbitrating it, and the invariants are enforced in code rather than by convention.

Process

How I build

A practical sequence rather than a formal methodology.

  1. Understand the product need

    Start with what the product has to do and who it is for, so the interface is built around real requirements instead of assumptions.

  2. Plan the frontend architecture

    Decide how components, state and data flow are structured before writing feature code, so the shape of the codebase is deliberate rather than accidental.

  3. Build responsive interfaces

    Implement the UI to work across the full range of screen sizes, using semantic markup and accessible interaction patterns.

  4. Integrate APIs and application behaviour

    Connect the interface to real services and handle the states that come with them — loading, empty, error and success.

  5. Test, refine, and maintain

    Check the result under real conditions, fix what does not hold up, and keep the code in a state that is straightforward to return to later.

About

A little more context

Chukwudi Praise is a Frontend Engineer working primarily in React, Next.js and TypeScript, with a full-stack engineering background. His work centres on responsive interfaces, frontend architecture that stays maintainable as a product grows, applications connected to real APIs, and product behaviour that holds up once it meets real data.

In practice that means keeping business rules out of the render tree where a tested module serves better, designing empty and error states alongside the populated ones, and treating accessibility as part of building a component rather than a later pass.

The full-stack background is deliberate, and it isn’t theoretical. I have scaffolded services in NestJS, built APIs in FastAPI and Express, designed relational schemas and their migrations, and shipped products where I wrote both the interface and everything behind it. That makes it easier to work across API boundaries, agree on data shapes early, and catch integration problems before they reach the interface.

He is currently focused on remote frontend engineering roles where interface quality and long-term maintainability are taken seriously.
